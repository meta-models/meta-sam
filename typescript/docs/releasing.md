# Releasing packages

The four TypeScript packages are published to the public npm registry under the
names checked into their manifests:

- `@meta-sam/parser`
- `@meta-sam/graphics`
- `@meta-sam/video`
- `@meta-sam/react`

Publication is automated by the `release npm packages` workflow
(`.github/workflows/release-npm.yml`) and gated by a human approval in the `npm`
GitHub environment. Nothing publishes from a pull request, a tag, or a branch
other than `main`.

## Versioning with Changesets

Meta-SAM uses the standard Changesets release-pull-request model.

1. A feature pull request that changes a published package adds a changeset with
   `npm run changeset`. The changeset names each directly changed package and its
   SemVer bump. Choosing a minor or major bump is a release decision, not an
   implementation detail.
2. After the feature pull request merges, the workflow creates or updates one
   rolling `chore: version packages` pull request.
3. Changesets expands exact internal dependency updates through the package graph.
   For example, a parser patch also versions graphics and React when their parser
   dependency changes; unrelated video code remains at its current version.
4. The release pull request commits package versions, exact internal dependency
   versions, changelogs, the regenerated
   [`conformance/compatibility.json`](../../conformance/compatibility.json), and
   `.changeset/release-plan.json` for human review. The plan is generated by
   `npm run version-packages`; do not hand-edit it.
5. Merging that release pull request runs the required browser validation and then
   the `publish` job, which waits for approval in the `npm` environment before it
   publishes exactly the planned package subset, in dependency order, under the
   `latest` tag.

The workflow can also be dispatched manually from `main` to retry either
release-PR generation or a reviewed publication. A manual dispatch from any other
ref stops at the version-job guard, so all dependent validation and publish jobs
remain skipped.

## Authentication

The publisher does not read or write registry credentials. In the `publish` job,
`id-token: write` lets npm exchange the workflow's OIDC token with npmjs.com
through [trusted publishing](https://docs.npmjs.com/trusted-publishers). Each
package's trusted publisher on npmjs.com must name this repository, the workflow
file `release-npm.yml`, and the environment `npm`.

The publisher deliberately does not force npm's `--provenance` flag. Trusted
publishing works for private repositories, while provenance does not. When the
repository is public, npm automatically generates provenance for OIDC publishes;
while it is private, the same OIDC release succeeds without an attestation.

npm can only configure a trusted publisher for a package that already exists. To
publish a package for the very first time, add a short-lived granular access
token as the `NPM_TOKEN` secret of the `npm` environment; the pinned Changesets
action prefers that token when present and falls back to OIDC otherwise. Remove
the secret and configure the trusted publisher immediately after the first
successful publish.

## Building archives

Build and audit the archives locally with:

```sh
npm run build
npm run release:archives -- --output .packs/release
```

For an immutable development build:

```sh
npm run release:archives -- \
  --output .packs/release \
  --version-suffix=-dev.123
```

The command writes one archive per package plus `release-manifest.json`. It fails
unless every manifest is publishable — not private, `"license": "SEE LICENSE IN
LICENSE"`, `repository` pointing at this repository and the package directory,
and `publishConfig.access` `"public"` — every archive carries the exact approved
SAM License bytes, every internal dependency pins the version the workspace
builds, and no archive contains local paths, internal hostnames, source maps, or
credential-shaped strings. The manifest records each archive's integrity so an
interrupted multi-package publish can safely verify and skip an identical version
on retry.

## What the publisher checks

`scripts/publish-npm.mjs` consumes the release manifest. Before the first
irreversible publish it validates every archive against the manifest digests,
reads each embedded `package.json`, and confirms that every internal dependency
either targets a package earlier in the same plan at its planned version or
already exists on the registry at that exact version with complete metadata.
Internal dependencies must be exact versions; ranges, aliases, and bundled
internal packages are rejected.

Publication uses a private read-only snapshot of each audited archive, so a
change to the source archive after preflight cannot change the published bytes.
After each publish the script reads the version back until the registry reports
the expected integrity and `latest` tag. The read-back budget is
`META_SAM_PUBLISH_VERIFY_ATTEMPTS` × `META_SAM_PUBLISH_VERIFY_DELAY_MS`
(default 12 × 10 s). `META_SAM_NPM_REGISTRY` points the script at a different
registry for testing.

Once every planned package is newly or already published and verified, the release
command reconciles the GitHub tag and release for each package. It prints
`New tag: <name>@<version>` for each release that does not exist yet; the pinned
Changesets action runs in `github-api` commit mode, so it creates the tag ref at
the workflow's `github.context.sha` and then the release. A release without its
tag fails closed.

### Recovering a half-published release

Tags and GitHub releases are created only after **every** planned package is
published and verified, so a publish that fails after some packages reached the
registry leaves the registry partially complete and the tags missing. Re-run the
failed `publish` job on the same workflow run.

Publication is immutable, so preflight reads each planned spec back, finds
matching `dist.integrity`, matching `version`, and the `latest` tag already
pointing at it, and prints `Already published and verified <spec>` without
republishing. Once every spec passes, the release command reconciles GitHub.

A re-run fails closed instead if the registry disagrees with the plan: different
bytes under a planned version, a `latest` tag pointing elsewhere, or incomplete
registry metadata all stop the run before anything is published.

## Consumers

Install the packages directly:

```sh
npm install @meta-sam/parser @meta-sam/graphics @meta-sam/video @meta-sam/react
```

The Python distribution is released separately; see
[`python/README.md`](../../python/README.md).
